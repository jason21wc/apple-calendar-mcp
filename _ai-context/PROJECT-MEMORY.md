## Founding Context

**Goal.** A local MCP server that lets Claude Code and Codex work with the current macOS
user's Apple Calendar — inspect calendars, retrieve bounded event sets, reason about
availability, and create, modify, and delete events under the containment controls
recorded in Key Decisions (**live set: C3-C7**; C1 withdrawn, C2/C2a/C4a superseded).

**Done looks like.** See the Definition of Done in `docs/IMPLEMENTATION-PLAN.md` §12 — the
repository-owned canonical plan. It covers the read surface as shipped and, in §6, the write
path, the guards and the permission matrix. **The plan was previously a copy of a file in a
private directory outside the repo, which is where much of the drift came from; that
dependency was removed on 2026-08-22.**

The earlier wording here was read-only-era text that directed testing **at the real
calendar**. That is now hazardous: the same executable can delete events. Integration
testing runs against a disposable calendar only, never real personal data.

**Non-goals (first release).** No network listener or remote transport. No telemetry or
analytics. No CalDAV connection. No Apple ID / iCloud credentials. No automatic update
mechanism. No reminders (`EKReminder`) — events only. No long-lived caching of EventKit
objects. No bulk mutation (see C5 carve-out). No prebuilt binary distribution
(source-only publication). No mutation of events with attendees or an external organizer (C6).

**Audience.** Built for the author's own use on a single machine, but **likely to be
published as open source on a public GitHub repository** (stated 2026-08-17). Not a SaaS,
not multi-tenant, no customer data, no money — hence `standard` tier, not `saas-ops`.

Publishing source is distinct from distributing binaries. Consumers clone and build
locally and sign with their own **stable self-signed certificate** (created once in the
login keychain), plus the hardened runtime and the calendars entitlement. No Apple
Developer ID and no notarization are required for that path — those become required only
if prebuilt release artifacts are ever shipped, which is a later, separately approved
phase. Note the earlier claim that hardened runtime was unnecessary was **wrong**; see
the signing decision below.

The public-release intent raises the security bar even though the deployment is personal:
defects protect (or fail to protect) strangers' calendars, not only the author's. Weigh
the write-capability decision below on that basis.

## Spec Summary

Native Swift stdio MCP server over EventKit, three internal layers — **`MCPLayer` →
`CalendarKit` → `EventKitAdapter`** as conceptual layers. On disk they are
`Sources/apple-calendar-mcp/{MCP,Calendar,EventKit,Diagnostics}` — the directory names do NOT
mirror the layer names, and the on-disk scheme wins. EventKit framework objects never leave the adapter boundary and are
converted to immutable DTOs before crossing it. `EKEventStore` is confined to one
dedicated thread behind an actor.

| Native Swift + EventKit, not AppleScript / sqlite / CalDAV | 2026-08-16 | AppleScript automation is unreliable under TCC; direct `Calendar.sqlitedb` access is SIP-blocked and unsupported; CalDAV requires credentials we refuse to hold. EventKit is the only supported path. |

Developer ID + notarization remain necessary only for prebuilt release artifacts — a later, separately approved phase. |
| Events only, reminders out of scope | 2026-08-16 | Inferred from the founding brief and confirmed; keeps the entitlement and tool surface minimal. |

Reason for the change: the original design put every human-readable field on the `propose` call, which is flagged `readOnlyHint` and therefore auto-approved and collapsed by hosts, leaving the call the human is actually prompted on showing only a UUID and an opaque token. A single match is precisely where skipping confirmation is most tempting and where injection would aim. |
| C3 — Two-phase propose/commit + per-event pre-state snapshot | 2026-08-18 | **AMENDED (gov-f551d84f9142).** `propose` returns a preview and a token; `commit` requires it. The `.ics` export clause is **withdrawn** — EventKit exposes **no ICS export API** (header-verified), so it was never implementable, and hand-rolling RFC 5545 would have written the entire calendar including notes and attendee email addresses to plaintext readable by the very agent being contained. Replaced by a **complete per-event JSON pre-state snapshot** in the journal, which carries the reversal data without the privacy regression. |
| C4 — Append-only mutation journal sufficient to reverse | 2026-08-17 | Every mutation records a complete pre-state field snapshot, the operation, and a timestamp — enough to reconstruct what the AI changed. |
| ~~C4a~~ — *(folded into C7)* Undo restores an *equivalent* event, and is a fully governed write | 2026-08-18 | Restore reconstructs title, times, location, notes, and recurrence from the journal snapshot. That is intended (it mirrors Apple's own "Delete All Future Events") and is not the bulk mutation C5 excludes. What stays excluded: operating on multiple distinct events in one call. Still deferred until C3/C4 are demonstrated working, including a real restore. |
| **C6 — Attendee / external-organizer handling** | 2026-08-18 | **AMENDED 2026-08-25 at the human's explicit decision (`gov-800ad831a848`, PROCEED, no S-Series trigger). The blanket refusal is WITHDRAWN and replaced by confirmation.** Mutating an event with attendees or an external organizer is now permitted **behind a per-call human confirmation that names the risk in plain words**: that the tool will remove the event through EventKit, that this may notify other participants, and that attendee/invitation state cannot be restored. The tool calls the operation **"remove"** and must never claim equivalence to Calendar.app's Decline. **Why the original refusal fell:** its recorded rationale was that notifying people is an irreversible act with a human audience — but notifying the organizer *is* the intended semantics of declining, which the human does manually and routinely, so the rationale proved weaker than the rule it justified. A second rationale, that EventKit cannot express the operation at all, was **also wrong**: `EKEvent.h:120-127` states that to cancel an event you remove it with `removeEvent:`. What EventKit genuinely lacks is only an explicit RSVP setter (`participantStatus` is `readonly`), which is why *setting RSVP status* stays refused while *removal* does not. **Conditional:** the Confirm tier has no verified mechanism behind it yet, so this authorizes the POLICY, not the shipping of writes — no mutating tool may ship until an approval round trip is demonstrated (BACKLOG #1). | **C7 — Every mutation must be restorable, with one named exception** | 2026-08-20 | **AMENDED 2026-08-25 (`gov-800ad831a848`), same decision as C6.** "Restore" still means *the information is back*, not that the original object returns — a new event carrying the same title, times, notes, location and recurrence satisfies it. **The narrow exception, accepted knowingly by the human: attendee and invitation state is NOT restorable and mutations that destroy it are permitted anyway, behind confirmation.** `attendees` is `readonly` in EventKit (`EKCalendarItem.h:97`), so a deleted invited event cannot be recreated with its participant list, and no design can change that. ## Constraints

**macOS grants no read-only calendar permission.** `requestFullAccessToEvents` is the only
authorization that permits fetching events, and it confers read *and* write. Therefore any
read-only property is a property of our implementation, never of the OS. Corollary: the
original read-only stance bought zero privacy reduction — the full permission was always
going to be requested. It only ever bought blast-radius reduction.

**Write capability: APPROVED under the containment model below** (human decision
2026-08-17, clearing governance escalation `gov-cec3bcaf6e71`, which triggered
`meta-safety-non-maleficence-privacy-security`). Controls C1, C2, C3 were later amended
and C6 added under `gov-f551d84f9142` (2026-08-18). The residual risk is accepted
knowingly: untrusted calendar text, sensitive personal data, and mutation capability
coexist in one loop, and the containment below reduces blast radius and improves
reviewability without eliminating the injection path. Any further change that weakens a
containment control requires another fresh governance evaluation.

**Same-uid containment is not achievable — record this in the README (required by the plan's
Definition of Done, §12, and restated in §7):**

> These controls reduce the blast radius of a mistaken or manipulated model. They do not
> defend against an attacker with filesystem write access as your user — such an attacker
> can truncate the journal and delete snapshots. Same-uid containment is not achievable
> without a privilege boundary this project does not have.

**Amended 2026-08-22:** the clause "edit the allowlist" was removed from this paragraph when
the wording was reconciled with the README, because C1 was withdrawn and there is no allowlist
to edit. Naming a file that does not exist in a security disclosure teaches a reader to look
for the wrong thing. The substance of the disclosure is unchanged and is not weakened: the
journal and snapshots remain same-uid writable.

This residual risk was **not** among those named in the original `gov-cec3bcaf6e71`
approval and is larger than the ones that were. C3's snapshots and C4's
journal are all files owned by the user's own uid, inside the blast radius of a coding
agent that has filesystem write access and can reach them without going through this
server at all. They defend against a *mistaken or manipulated* model, not a *compromised*
one. Recorded rather than left implicit, per `meta-safety-transparent-limitations`.

**Same-uid write means impersonation, not merely bypass.** Recorded 2026-08-19 after a
security audit; this is a residual risk larger than the one previously named, and it was
not among those accepted in `gov-cec3bcaf6e71` or `gov-f551d84f9142`. The setup chain
assembles a silent code-signing oracle: `make-signing-cert.sh` installs a **trusted root
for code signing**, `trust-signing-cert.sh` puts `codesign` on the key's partition list so
signing needs **no password and no dialog**, the TCC designated requirement is
**identity-based** (gotcha 26), and the grant is keyed to an **absolute path** (gotcha 25).
Both halves of the requirement are attacker-supplied. Any same-uid process can compile,
sign silently, write to the granted path, and hold Calendar access attributed to this
tool — no prompt, no journal, nothing unusual in System Settings. The property that makes
the design work (rebuilds keep the grant) is exactly what makes the grant stealable.
Mitigation is deployment, not code: **install at a root-owned path and never grant to a
binary inside `.build`.**

**Host-side approval is not a control.** It is an assumption about the user's
configuration that the server cannot observe. If a commit tool is allowlisted in
`/permissions`, or the session runs with approvals bypassed, there is no prompt at all.
Two hardening claims made on 2026-08-17 were false and are withdrawn: "a bypass needs a
restart, which needs you" (clients respawn stdio servers on session start, reconnect,
crash and config reload, with no human action) and "logged to stderr so tampering is
visible in the transcript" (MCP server stderr goes to a log file, not the transcript).

**Calendar content is untrusted external data.** Titles, notes, locations, URLs, organizer
and attendee names, and calendar/source names are all attacker-influenceable via inbound
invitations and synced calendars. Per `meta-core-separation-of-instructions-and-data` and
`coding-quality-workflow-integrity`, none of it may ever be interpreted as instructions,
configuration, file paths, or shell input.

**EventKit identifiers are not permanent.** They can change on calendar moves and full
syncs, and fetched objects go stale after `EKEventStoreChangedNotification`. No long-lived
caching in v1.

| 83 | **The 2026-08-22 write-prompt test was overdetermined THREE ways, and the tools chosen were the two in that server's surface guaranteed not to prompt.** (a) `toolPolicy` was never set; (b) the governance proxy is an order gate that consumes no verdict (gotcha 67); (c) **the server itself never asked** — `apple-mail`'s `create_draft` elicits only when `send_now=True`, and its `delete_draft` deliberately has no elicitation at all ("recoverable from Trash"). Any one of the three fully explains the silence, so the result attributes to nothing. **To isolate a layer, pick an operation where the OTHER layers are known to be active or known to be absent — a null result from a stack of sufficient causes is not evidence about any of them.** | 2026-08-22 |
| 84 | **Server-initiated elicitation is available to us and does NOT depend on the user's host configuration — but it does NOT fail closed by default, and the first version of this entry said it did.** Verified in the pinned MCP Swift SDK 0.12.1: `Server.requestElicitation(message:requestedSchema:)` exists and calls `validateClientCapability(\.elicitation, "Elicitation")` — **but that validator's entire body is wrapped in `if configuration.strict`, and `Configuration.default` is `strict: false`.** Our server passes no configuration, so the check is a **no-op today**: calling `requestElicitation` against a client that never declared the capability would send the request rather than refuse. Same shape as gotcha 35 — a guard that only fires in a configuration we do not have. The fix is not to enable `strict` and trust it, but to **make our own explicit check and refuse**, because a control we implement is one we can test. Client capabilities ARE reachable: `server.start(transport:initializeHook:)` hands us `(Client.Info, Client.Capabilities)` at initialize; `clientCapabilities` is otherwise `private`. **Still unverified: whether Claude Desktop / Cowork declares the elicitation capability at all.** | 2026-08-22 |
| 85 | **`elicitation != nil` is the wrong check — the capability has sub-capabilities.** `Client.Capabilities.Elicitation` carries separate `form: Form?` and `url: URL?` (`Client.swift:101-121`). A client declaring URL-only elicitation satisfies a top-level check while `requestElicitation(message:requestedSchema:)` — the FORM variant — is unsupported. Any gate must test `elicitation?.form != nil`. Strict mode does not save this either: `validateClientCapability` takes a keypath to the top-level capability only. | 2026-08-23 |
| 86 | **`requestElicitation` has no timeout, and racing a task around it abandons rather than cancels.** `sendAndAwait` does `try await task.value` with nothing bounding it, and the request sits in `pendingRequests` keyed by id. A client that declares the capability and then never answers strands the tool call for the process's lifetime. Wrapping it in a timeout leaves the pending entry behind. **Same class as BACKLOG #19** — an unbounded wait on an external party — so whatever answer that produces should cover this too, and a human-approval design that can hang is not obviously better than one that can be skipped. | 2026-08-23 |
| 87 | **EventKit has NO trash, undo, or recovery API of any kind — grep-verified across every header.** `removeEvent:span:error:` is terminal; there is no recycle bin, no "recently deleted", nothing to restore from. This is the single biggest asymmetry with mail-shaped permission models, which get a recoverability floor free from the platform and can therefore rate a delete as low-risk ("recoverable from Trash"). **Calendar has no such floor: the only recoverability is the one we build (C7's journal snapshot + reconstruct), and it is not built.** Any permission taxonomy borrowed from a mail server must be re-calibrated on this point, not copied. (`EKEventStore.h:254-275`; zero matches for trash/undo/recover/restore across `EventKit.framework/Headers`.) | 2026-08-24 |
| 88 | **The MCP spec puts human-in-the-loop at SHOULD, and annotations at untrusted.** Verified at the 2025-06-18 spec: *"there **SHOULD** always be a human in the loop with the ability to deny tool invocations"*, and *"clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers."* Consequences for this project: (a) **no client is obligated to prompt for anything**, so a design that assumes prompting is assuming a courtesy; (b) `destructiveHint` can never *deliver* an approval, only suggest one — which is why an "approval required" column in any permission matrix must name a MECHANISM, not an annotation. The spec also lists unknown tools under **protocol** errors (BACKLOG #22 is correct), tells servers to rate-limit invocations (we do not), and tells clients to implement tool-call timeouts (relevant to the unbounded elicitation wait, gotcha 86). | 2026-08-24 |
| 89 | **A protocol standard does not prove that a framework call triggers the protocol action.** RFC 5546 defines the semantics and authority for organizer `CANCEL` and attendee `REPLY`; it does not say that `EKEventStore.removeEvent` on this macOS/account emits either one. `EKParticipantScheduleStatus` (`EKTypes.h:93+`) proves EventKit represents invitation-delivery state and may not know the delivery outcome; it does not bridge that causal gap. The standards strengthen C6's risk basis, but the second-account integration test remains necessary and the exact delete behavior is still unmeasured. | 2026-08-24 |
| 90 | **Google Calendar's `sendUpdates` is a useful comparative API, not an industry standard.** It separates a mutation from the choice of which guests receive updates (`all` / `externalOnly` / `none`). EventKit's public headers expose no equivalent suppression parameter — only scheduling state. That means this server cannot promise notification suppression: approval can acknowledge outbound risk, but cannot control it. Refusal is therefore the strongest available policy for attendee/external-organizer events, without claiming Google proves universal practice or that every EventKit mutation sends a message. | 2026-08-24 |
| 91 | **EventKit exposes no explicit RSVP/Decline setter.** `participantStatus` is `readonly` (`EKParticipant.h:50-54`), and no public RSVP-setting method exists. That does **not** prove `removeEvent` cannot be translated by the account backend into a decline. For an event the user organizes, EventKit explicitly says cancellation is performed by `removeEvent` (`EKEvent.h:121-128`); for an invitation organized by someone else, the resulting RSVP/sync semantics remain unmeasured. The server can truthfully promise only that it requests removal, not that this is equivalent to Calendar.app's Decline. `organizer.isCurrentUser` is readable, so organizer cancellation and attendee removal can be presented separately. | 2026-08-25 |

| Requirement | Status |
|---|---|
| Reading must **never** ask for permission | **Met.** Read tools carry `readOnlyHint: true` and do not prompt (measured in Claude Desktop 2026-08-20) |
